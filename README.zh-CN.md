## 主要结论

- CMP 170HX 10G：单请求下，与 **MTP 关闭**相比，**MTP 开启**在有效的
  1K-20K 输入、1K-8K 输出矩阵中将端到端生成吞吐提升 **1.79x-2.27x**；
  最大并发 4 的五个有效用例提升 **1.65x-1.89x**。
- CMP 170HX 8G：相同口径下，**MTP 开启**相对 **MTP 关闭**的单请求提升为
  **2.07x-2.82x**，最大并发 4 提升为 **2.07x-2.54x**。
- MTP 优化的是生成阶段，不会加速 prompt prefill。两张卡在 MTP 开启后，
  六个 prefill 点的 TTFT 均高于 MTP 关闭状态。
- 两张卡在 MTP 关闭时的单请求吞吐只相差约 0.8%-10.4%；MTP 开启时，8G
  数据高出约 19.6%-50.5%。8G 数据中的 MTP 接受长度为 4.00，本机 10G
  数据为 2.91-3.50，这是 MTP 开启结果差距明显扩大的直接线索。
- 这些数据适合比较同一张卡上 MTP 开启与关闭的收益，也适合观察两次测试的结果差异；
  它们不是只改变原始显存规格的严格硬件 A/B，不能把差值直接归因于 10G 或 8G。

## 如何测试

复制示例配置，填写 SGLang、模型、context、MTP 和功率参数，然后运行标准管线：

```bash
cp configs/benchmark.example.env /tmp/my-benchmark.env
sudo -E scripts/run-standard-suite.sh /tmp/my-benchmark.env
```

管线会读取服务实际 token pool，自动计算每个输入/输出/并发组合是否能运行；小显存
机器保留容量跳过项，大显存机器继续运行 extended 长上下文矩阵。结果位于
`runs/<RUN_ID>/`，包含 metadata、容量/显存/KV 记录、CSV、Markdown 和 PDF。
自定义模型及完整字段说明见
[`测试与发布规范`](CMP-170HX-Benchmark-Protocol.zh-CN.md)；AI agent 必须同时遵守
[`AGENTS.md`](AGENTS.md)。容量规划、CSV/Markdown/PDF 生成已通过离线 fixture；
新通用启动与执行器仍需用首个真实模型 run 完成端到端验收。

## 如何理解两张卡的差异

最终显存容量决定模型、KV/GDN state、CUDA Graph、上下文和并发能否装下，但相同
token pool 已经能装下时，空闲显存不会直接变成计算吞吐。这里，MTP 关闭结果很接近，
而 MTP 开启结果的差距明显扩大；同时 8G 数据的接受长度为 4.00，10G 数据为
2.91-3.50。更高的接受长度意味着每次 target verification 能确认更多 draft
tokens，完成相同输出所需的 speculative cycles 更少。

两次测试仍可能存在 SGLang 代码、固件、持续频率、HBM、散热和平台状态差异。
所以并列表格展示的是两次实测之间的差值，不证明原始 8G 规格或最终 64 GiB 容量
本身带来了对应的速度提升。
